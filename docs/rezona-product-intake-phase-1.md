# REZONA — تدقيق إدخال المنتجات والمخزون والكتالوج

**2026-11-16 | المرحلة 1: مراجعة وقياس أولي، قبل تغيير التطبيق**

راجعت نسختَي العمل في `AboEssa` و`AboEssaMobile` عند `4f83036` و`a786986` مع التعديلات المحلية الموجودة مسبقاً. هذا التقرير لا يفترض أنها منشورة. لا تغييرات على الكود التشغيلي أو قاعدة البيانات أو السيرفر، ولا إرسال صور إلى مزود خارجي. نطاق المخزون الجديد هو **منتجات البيع الثابت**؛ المزادات تبقى كياناً منفصلاً، وتستفيد من تحسين الصور والكتالوج من دون تغيير المزايدة أو الدفع.

### مسارات العرض الحالية

- **الرئيسية / البحث / فئات الرئيسية**: `CustomerMarketplaceCubit` ينتظر الفئات أولاً، ثم طلبَي `GET /api/marketplace` (20 منتجاً و20 مزاداً)، ويعرض بالتناوب حتى 20 فقط. تكرار نفس pagination على المصدرين ثم قصّ الناتج يمكن أن يُسقط عناصر لم تُعرض. لا يمنع Cubit رد بحث/فلتر قديم من وصوله بعد الأحدث. البحث عند الإرسال، لا عند كل حرف. يوجد طلب منفصل لعارضة الإعلانات.
- **المتجر والخصومات**: `GET /api/products` مع `categoryId` أو `discountedOnly`. `GridView.builder` موجود؛ الصفحات لا تُلحق صفحات إضافية تلقائياً. تفاصيل المنتج من `GET /api/products/:id`؛ الكروت والتفاصيل تقرأ أول URL أو معرض الروابط. المفضلة تستخدم لقطة محفوظة تحتاج تحديث إصدار الصورة. صور طلبات الزبون تاريخية ولا تُستبدل عند تحديث الكتالوج.
- **الأدمن**: `GET /api/admin/products` و`/:id` عبر نفس ProductListing. الكونسل عنده search مؤجل وpager؛ نموذج المنتج القديم والأدمن الجديد يحتاجان نفس اختيار variants. لا شاشة اختيار مخزون/مستودع حالياً. نُبقي قوائم المزاد وتفاصيله ومنتجات الإعلان والطلبات ضمن مراجعة المستهلكين، مع عدم تغيير دلالة الصور التاريخية.
- **SQL/API**: [ProductsService](../src/products/products.service.ts) يستخدم offset وcount لكل صفحة،`limit` افتراضي 20 وأقصاه 100 مع tie-breaker بالـID. القائمة تحمل الفئة والمشتري والطلب حتى لسياق الزبون؛ آخر اثنين لا يظهران في JSON العام، لكن يُقرآن من DB. القائمة ترسل الوصف وكل روابط الصور. [MarketplaceService](../src/marketplace/marketplace.service.ts) يقرأ حتى `offset + limit` من كل مصدر ثم يفرز ويقص في الذاكرة، ويفرز بعض الحقول بعد أخذ شريحة بترتيب مختلف، فلا يضمن ترتيباً عالمياً لها. مع 10,000 نتيجة، طلب الصفحة 500 بحجم 20 قد يقرأ حتى 10,000 سجل من كل مصدر مؤهل. هذا حد من الكود، ليس زمناً مقاساً. `contains` غير حساس للحالة على الاسم والوصف؛ لا تطبيع عربي أو فهرس بحث مخصص. لا دليل N+1 من اختبار SQL بعد؛ لازم نسجل الخطط وعدد الاستعلامات قبل الفهارس الجديدة.

### الخطر الأعلى: توافق حساب المخزون

المهاجرة الحالية تفرض `totalQuantity = availableQuantity + soldQuantity` وعدداً غير سالب. إنشاء المنتج/تعديل الكمية يغير الإجمالي، الشراء يحجز الكمية عبر تحديث شرطي داخل معاملة Serializable ويكتب الطلب والدفع، وإلغاء الطلب في [AdminConsoleService](../src/admin-console/admin-console.service.ts) يعيد المخزون. الإلغاء يعدّ **سطور** الطلب حالياً، لذلك يجب اختبار مشتريات متعددة الوحدات وملفات الطلب القديمة قبل الربط، وحساب وحدات الإرجاع من السجلات نفسها. تنفيذ رفوف بمسار إدخال مستقل سوف يجعل مخزون الرفوف مختلفاً عن المتجر. كذلك idempotency لشراء المنتج يفحص ثم يحفظ الـreplay خارج المعاملة؛ لا نكرر هذا النمط في عمليات المخزون الجديدة، ونغطي الشراء المتزامن عند توصيل ledger.

**خطة إعادة القياس:** على نسخة محلية مع قاعدة staging معزولة وعينات 20/1,000/10,000 سجل متنوّع، قِس API P50/P95 لكل endpoint، عدد الاستعلامات والصفوف وخطط `EXPLAIN (ANALYZE, BUFFERS)` على SELECT فقط، payload مضغوط وغير مضغوط وحجم 20 صورة أولية. [أداة القياس الحالية](../scripts/local-read-load.mjs) مقيدة بـlocalhost؛ تمديدها لاحقاً يفصل الإحصاءات حسب المسار ويضيف تفاصيل/فلاتر ووقت اتصال محدود. على هاتف حقيقي بنمط Flutter profile وشبكة ثابتة التشكيل، قارن أول كارت وصورة، وقت الصفحة، dropped frames، heap وطلبات الصور أثناء تمرير 200 كارت، وإعادة فتح البرنامج من القرص. شغّل نفس seed والجهاز وشروط الشبكة قبل/بعد، بارد ودافئ؛ لا تُستخدم بيانات الزبائن ولا load test على الإنتاج. مستهدف المشروع: أقل من 1s للكاش، وحوالي 2.5s للتحميل البارد حيث يمكن، وبلا ادعاء تحقيق قبل القياس.

داخل Flutter: مكوّن صور مشترك حسب مساحة الرسم وDPR، decode bounded، كاش قرصي بحدود عمر/سعة وprefetch محدود قرب الشاشة. لا كاش قرصي مشترك للصور الخاصة. مفاتيح ميتاداتا تشمل API origin/البيئة، المستخدم أو guest، اللغة والفئة والترتيب والفلتر/البحث والـcursor. load next dedup + request generation/cancellation وحماية الرد المتأخر. ابدأ بكاش بيانات محدود داخل repository وTTL قصير للأسعار/المخزون + refresh on focus؛ stale يظهر كمعلومة وليس تفويضاً للشراء. حدث تغيّر منتج بعد commit يبطل العناصر المتأثرة، ولا يبث بيانات زبون. لا تعميم public-cache على `/api`؛ خصوصاً marketplace يسترجع حالة مزايدة خاصة بالمستخدم.

### ترحيل آمن — تصميم، لا SQL مطبّق

1. **Expand**: جداول إضافية وصِلات nullable، قيود وفهارس مدروسة. `FileAssetVariant(assetId,recipeVersion,format,kind)` فريد مع content hash؛ `ProductMedia` روابط مرتبة للأصل/المعتمد، ولا تغيير order snapshots. legacy URL داخلي فقط يطابق asset موثوق؛ لا تحميل URL يرسله مستخدم/AI. سكربت seed الحالي قد يكتب فوق مفتاح ثابت؛ immutable الجديد لا يسمح باستبدال محتوى مفتاح قديم.
2. **Identity**: metadata إضافية للمنتج، `verifiedIdentityKey` اختيارية وفريدة حين تتحقق هوية SKU؛ تخزين GTIN كنص مع الأصفار. افحص الاصطدامات قبل فرض unique؛ قيم AI والكتابة التاريخية ليست تلقائياً verified. لا إعادة إنشاء product IDs ولا حذف سجل متشابه.
3. **Backfill**: خزّن الرصيد الحالي لكل منتج كمهاجرة موثقة إلى موقع افتراضي **غير موزع**، ولا تدّعي معرفة رف فعلي من النظام القديم. تخصيص الأرفف جرد لاحق. دفعات بمفتاح فريد وعلامة تقدّم، مع قفل المنتج عند seed والتحقق، لا تغيير `availableQuantity` في العملية ولا نقل منتج صفر. قبل اعتماد المخزون اختبر مجموع الأرصدة والقيود والـrow counts وعلاقات الطلبات.
4. **Cutover منسق لكل الكتابات**: نشر نسخة تجمع القديم والجديد قبل فتح إدخال الرفوف. موائم للأدمن القديم يقبل الكمية القديمة ويترجم الفرق على الموقع الافتراضي ضمن السياسة، أو يطلب ضبط الموقع لتصحيح فعلي دون أن يكتب فوق عدة رفوف؛ يوثّق هذا في خطة rollout. اختر ترتيب أقفال ثابت، allocate البيع من مواقع محددة داخل المعاملة، سجل allocations لإرجاع فعلي صحيح. طلبات ما قبل الترحيل تعاد إلى غير موزع عند غياب allocation. إذا بقي حجز مستقبلي قبل الالتزام، `available = onHand - reserved`؛ شراء اليوم يخصم مباشرة داخل معاملة الطلب، فلا نخترع حجزاً مزدوجاً. بيع المزاد والمحفظة والخصومات تبقى بدلالتها الحالية.
5. **Exactly-once أثر التطبيق**: مفتاح unique على العملية وممثلها مع hash للحمولة، claim وbalance وmovement وreceipt في نفس المعاملة. إعادة نفس الطلب ترجع نفس الاستجابة، المفتاح المختلف يمر كعملية مستقلة، نفس المفتاح بحمولة مختلفة 409. publish فريد لكل draft، وقيد مستقل لحالة الباركود الموثوق. اختبر race في PostgreSQL حقيقي، لا mocks فقط.
6. **الرجوع**: عطّل الميزات الجديدة بالـflags، وتراجع إلى نسخة تعرف dual-write بعد فتح المخزون؛ الرجوع لبناء قديم يكتب الإجمالي منفرداً يتطلب أولاً إيقاف الكتابات ومصالحة الرصيد أو restore مختبر. لا drop للأصول أو الأعمدة أو علاقات الطلبات. إجرائياً: backup DB+MinIO → staging/migrate → تحقق الصفوف → نشر متوافق flags off → backfill → staff pilot → توسعة ومراقبة.

### المسودات والعمليات بالخلفية

`ProductIntakeDraft` له حالة عامة مستقلة عن `recognitionState` و`duplicateState` و`imageState`، وowner وrevision. `IntakeJob` يملك `draftId + sourceRevision + jobType + generation` فريدة، وprovider/model/prompt version/hash/status/attempt/provider job ID/usage وانتقال آمن. نسجل طلب العمل بصورة مستمرة ثم نرسله بمفتاح BullMQ ثابت؛ عامل reconciliation يعيد enqueue للمفقود. يحتفظ بالـprovider ID فور استلامه؛ إذا صار timeout غامض وقت الإرسال لا إعادة توليد مدفوعة عمياء. إلغاء/retake يرفع النسخة ويمنع نتيجة متأخرة، وقرار الإلغاء لا يغير مخزوناً. تبقى form edits مستقلة عن نتيجة العمل. بدء بـpolling متفاوت ومحدود فقط للحالات المعلقة مع pause عند الخلفية؛ sockets الخاصة لاحقاً تعرض إشعار ID وليس المحتوى. Limit للرفع قبل buffering، أنواع/حجم/بكسلات، وعدم تمرير محتوى الملصق كتعليمات أو قبول URLs من النموذج.

تخزين الأصل والمعاينات الخاصة خارج المسارات العامة، وصول مفوّض و`no-store`، وسياسة retention/cleanup مع حماية الأصول المشار إليها. WebP/JPEG بأسماء صريحة يسمحان بكاش edge بلا تفاوض خطر. أبقِ MinIO، وافحص CDN الحالي بهيدر `CF-Cache-Status` قبل أي تغيير DNS أو اشتراك جديد. [سياسة كاش Cloudflare](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/).

**عقود مقترحة:** أضف مسارَ قراءة كروت `/api/catalog/products` بحقول العرض والـcursor، ووسائط اختيارية لتفاصيل المنتج؛ العقد القديم نفسه يبقى للنسخ المنشورة. تحت `/api/admin/product-intake` تستخدم المسودة create/upsert بمفتاح التقاط، GET list/detail، PATCH مسودة بـrevision، ثم upload/analyze/approve/publish/cancel حسب الحاجة. مسارات المخزون منفصلة تحت الأدمن: lookup للمواقع، رصيد لكل منتج، stock-in/transfer/adjust. كل تغيّر رصيد يتحقق من `Idempotency-Key` ومن دور الموظف ومن أن المنتج والموقع متاحان. لا تُفتح مسارات المخزون ولا إدخال الذكاء بمجرّد نشر schema؛ صلاحياتها وتوابعها تُختبر أولاً.

## 5. بوابة المرحلة التالية

ابدأ بمرحلة الصور فقط: لا تغيير لوظائف الدفع والمخزون أو روابط العملاء الحاليين. قبل اعتمادها: ابدأ بملفات fixture هذه في بيئة معزولة، سجّل زمن/حجم/جودة variants، وجرّب backfill مرتين للتأكد من عدم التكرار، ومع فشل MinIO أو decode يُعاد عرض الأصل. لا تفعيل على الإنتاج قبل تجربة العملاء القدامى والجدد وبقاء المنتج/المزاد ظاهرين. تبقى العينة الموسومة للـAI، قياسات PostgreSQL/الجهاز، مفاتيح المزود، ونتائج الجودة والنشر بوابات لاحقة وليست نتائج منجزة.
